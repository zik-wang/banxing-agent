# 草稿持久化失败后的离线恢复候选

本轮只在独立目录使用明确标记的合成数据；没有读取或复制公司材料，没有Qwen/DeepSeek调用，没有重跑已完成的模型对比，也没有修改生产运行版本。

## 复现确认了什么

使用约7.5MB合成索引，直接执行现有ResourceSpace、Continuity、DocumentTools及草稿保存代码。在目标设置为只读、以及本测试持有不允许删除共享的Windows文件句柄时，原子rename均返回EPERM，8次有界尝试后停止；旧索引仍可解析且哈希不变，旧TXT成果未损坏。仅通过释放本测试创建的句柄即可让同一操作继续保存；没有关闭未知进程或修改系统ACL。

另一个缺陷得到直接证明：草稿JSON和本地状态已写入，随后共享检查点失败。旧版重试直接返回内存中的草稿，却没有补存检查点；新会话从旧检查点恢复时找不到这份正文。原子替换失败与这项恢复缺陷要分别看。

这些受控条件说明EPERM的可能机制，**不能证明生产故障的锁持有者或权限根因**。此前Windows占用快照没有报告进程，也不能证明没有临时或受保护的占用。

## 最小代码修复

- 草稿本体独立原子保存，已有同版本草稿校验后复用，保留原创建时间和字节；不因内存缓存丢失而重写原稿。
- 检查点失败后明确返回原错误及“正文已本地保存、持久化待恢复”的草稿引用。再次保存会真正补存检查点，不用缓存成功掩盖失败。
- 只在同一获授权任务的resume/retry中，按版本、正文哈希及来源校验恢复本地草稿，并向工具上下文提供可引用的draft_ref。恢复草稿仍是不确定正文，不是已核实事实或已交付文件。
- 临时索引文件不自动覆盖后来提交的状态；未提交的草稿临时文件单独登记为告警，不当作完成稿。其他工作项不能借此获得草稿。
- 已注册成果缺失/篡改仍保持原有阻断；本修复不把失败任务自动改为成功。
