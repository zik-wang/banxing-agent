# SF 共享单槽接入记录

worker-05 已把本机有限诊断与 DSH 文档试跑的后续 SF 请求接到同一共享调度入口。每次只包一层，**收到响应头不释放槽位，JSON/SSE 完整读取结束后才返回调度回调**。本提交提供可注入调度器的 relay 和合成测试；本机认证、端口、DSH 配置及运行态不上传。

## 实际接入

- 有限案例：本机 `run-queued-case.mjs` 调用现有 `withSiliconflowSlot`，获槽位后才启动原监督器及请求。原300秒请求时限从获准执行后开始；子入口还核验共享服务中的worker与lease，拒绝直接启动或假环境标志。旧直连序列/流式诊断入口已封住，历史成绩未改。
- DSH：SF provider 指向本机 `createSiliconflowRelay`，实际上游仍是原获准的 SF 端点与 `Qwen/Qwen3.8-27B`，模型JSON正文原样传输。永久服务器本身不占租约，每个有限HTTP请求独立调用共享槽位。DeepSeek连接没有改，不占SF槽位。
- 客户端允许等待共享队列，供应商仍保留原300秒时限；准备、排队与供应商耗时分别记录。客户端排队条件已变化，不能改写历史对照或把新总耗时直接归因于框架。
- 本机接线代码已在调度器登记真实 `drained worker-05`；执行前核实了旧诊断进程退出及DSH无运行中会话，接入状态用原上报命令登记 `SF_QUEUE_READY`。登记时仍待worker-04收尾，没有旁路发起新SF请求。

## 完成与异常边界

模块只接受既有模型及chat/models路由，认证由原客户端提供，不记录请求头或正文。请求正文只记录字节数和哈希。

正常JSON/SSE读到上游EOF后，回调返回状态及Retry-After，由现有共享服务统一处理间隔和429冷却；模块不另开重试。下游客户端提前断开时仍消费已在途的上游响应，不能提前让另一请求占槽。网络/超时导致完整消费无法确认时返回 `uncertain`，保留租约，不自动抢占。

队列/暂停检查失败时不请求供应商。health、无权限或无支持路由不占槽位；SF以外的提供商不经过该relay。全局单槽按本机控制规则执行，不能把不同API Key当作不同账户额度，也不宣称平台所有模型的配额本来就是共用一个。

## 验证

```powershell
node --test tests/v8-sf-relay.test.mjs
```

7项离线测试覆盖：完整JSON、完整SSE、429完整错误体及Retry-After向调度器传递、网络不确定保留、无支持路由不占槽、下游断开不提前释放、暂停时不访问供应商。测试仅使用本地HTTP和注入的模拟上游，不使用真实SF Key或公司材料。

首次随机端口测试遇到fetch禁止端口，测试及本机启动器已改用受控高端口并重跑。当前没有把模拟429当作真实平台限流，也没有把本地接线和单元测试冒称跨窗口真实排队成绩。真实共享队列的迁移等待、60秒间隔、暂停截止及租约归属由现有调度器控制，本模块不修改它。

本机已启用的范围为本窗口有限诊断和独立DSH试跑，未擅自改其他worker入口或正式网站；登录、绝对路径配置和队列状态保留在本机。后续若扩展模型/端点，须重新核对授权并接同一个共享入口。
