# Editable composer, queued messages and branches

The composer stays editable while a task runs, uploads proceed, a request is in flight, or a conversation loads. Sending still requires a ready target and completed upload. A submitted message during ongoing work is durably queued, visibly marked as waiting, and executed sequentially after preceding work. It is not live injection into an in-flight model request. Queued input file IDs are pinned; messages can be edited or deleted until dispatch. Client request IDs prevent duplicated submissions after ambiguous network responses. Queue state survives service restarts.

Drafts are maintained separately per conversation for switches in the current page session. Sending clears the submitted text immediately; delayed acknowledgements do not clear newly typed text. A failed request retains its original text, request ID and file selection separately, allowing retry while preserving a newer draft. Drafts themselves are not promised to survive a full browser restart.

Completed or running historical messages are immutable execution evidence. Editing creates a revision branch before the selected message and submits replacement text. Deleting creates a branch before the selected message, excluding it and subsequent turns. An explicit fork includes the selected completed turn, exact result reference and earlier history. Unfinished source replies are not copied as completed results. Branches have independent work-item selections and a return-to-source control. Original conversations, files and receipts remain available. The UI labels historical deletion as a branch operation and requests confirmation.

The regular single-worker tool runtime remains in place. Queue acceptance does not imply immediate model execution. File uploads into an actively processing conversation still wait, while typing remains available. Queue and branch operations do not grant new file authority or perform hard deletion of user files.
